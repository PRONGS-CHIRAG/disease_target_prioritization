# Milestone 5 — Progress Record

What was actually built against [milestone5_plan.md](milestone5_plan.md): a
Next.js frontend replacing the Milestone 3 Streamlit app, and the FastAPI
completion that frontend needed to reach parity. See that plan for the
reasoning behind each decision; this document records what happened when
the plan met real code, real data, and a real browser.

---

## 1. What was built

**Backend (`src/target_prioritization/`)** — frozen except one named
carve-out:

- `presentation.py` (new) — scenario presets (with stable slugs), dimension
  labels, standing limitations, not-buildable reasons, lifted out of
  `app/common.py` before it was deleted, so both the old Streamlit app and
  the new frontend read the same constants during the migration window.
- `api/schemas.py`, `api/main.py` — completed. Seven endpoints
  (`/api/meta`, `/api/diseases`, `/api/diseases/search`,
  `/api/diseases/{id}`, `/api/rank`, `/api/evidence`, `/api/health` +
  root `/health`), all five ranking filters (was two), scenario weights,
  the sort toggle, and a real `EvidenceBreakdown` (was missing
  `evidence_diversity`/`functional` outright — a genuine pre-existing bug,
  independent of the pathways/expression/network question below).
- `api/cache.py` (new) — `lru_cache`-wrapped `cached_features()` /
  `cached_app_data()`, replacing what Streamlit's `@st.cache_data` was
  doing with no FastAPI equivalent.
- `models/train.py` — `@cache` added to `load_fitted_xgboost` (keyed by
  path), the plan's one exception to "services stays frozen": no injection
  seam existed for the fold model the way `features=`/`weights=` exist for
  frames.
- `frontend_checks.py` + `scripts/check_frontend.py` (new) — six checks
  against real artifacts, mirroring `app_checks.py`'s pattern; all six
  pass against all ten configured diseases.

**Frontend (`frontend/`)** — new. Next.js 16 (App Router, Turbopack —
current stable at scaffold time; plan named 15), TypeScript strict,
Tailwind v4, shadcn/ui, TanStack Query, TanStack Table, `nuqs`, Recharts,
`openapi-fetch` against types generated by `openapi-typescript` from the
live OpenAPI schema (`make types`). Four routes — `/overview`, `/ranking`,
`/evidence`, `/compare` — no dynamic segments (§2 below). Design direction:
an "instrument panel" aesthetic reusing `viz.py`'s validated dimension
palette (Source Serif 4 / IBM Plex Sans / IBM Plex Mono), with a signature
"score strip" — a stacked bar of the exact per-dimension contributions —
repeated at three sizes across the ranking table, the evidence page, and
the comparison view.

`app/`, `scripts/run_app.py`, `make app`, and the `streamlit` dependency
are gone (`git rm -f`, since three of the five files carried uncommitted
Phase-0 edits from earlier in this same migration).

## 2. Findings the plan's own text didn't anticipate

### 2.1 The pathways/expression/network claim in the original plan draft was wrong

The plan's first draft said `/rank`'s `pathways=None, expression=None,
network=None` was stale and should start reporting real Milestone 4
values. Investigation before writing code found the opposite:
`_DISPLAY_DIMENSIONS` (`services/target_ranking.py`) is a hardcoded
5-element list that structurally never carries those three, and
Streamlit's own ranking table never displayed them either. Populating them
would have been new evidence display, not parity — the plan text was
corrected in place (§1, §4.1) before implementation, rather than
discovering the mismatch mid-build.

### 2.2 Next.js 16 shipped between plan and build; two real adaptations

`frontend/AGENTS.md` (generated by `create-next-app`) instructs reading
`node_modules/next/dist/docs` before writing App Router code, since this
version has breaking changes from training-data-era Next.js. Two things
that changed the plan:

- **`output: "export"` and `rewrites()` are mutually exclusive**, enforced
  for `next dev` too, not just `next build`. The plan's dev-mode API proxy
  depends on rewrites. Fixed by gating `output`/`rewrites` on a
  `BUILD_STATIC_EXPORT` env var in `next.config.ts`, set only by
  `make frontend-build` / the Dockerfile — dev keeps the proxy, the
  production build gets the export, from one config file.
- **`useSearchParams` (which `nuqs` calls internally) needs a `Suspense`
  boundary to prerender under static export**, even for an all-client-
  component page. Missing this failed the static build outright
  (`next build` errored on `/evidence`) rather than degrading gracefully.
  Fixed by wrapping every page's content component in `<Suspense>`, plus
  one more boundary around `<AppShell>` in the root layout, since the
  shell's own disease picker reads the same hook.

Given both, the plan's fallback (disease AND target as search params, no
dynamic route segments at all) was adopted outright rather than attempted
first — it sidesteps `generateStaticParams` entirely and turned out to be
the right call independent of the YAML-coupling concern that originally
motivated naming it as a fallback.

### 2.3 A real bug the plan's invariants didn't specifically name

The ranking table's mini "score strip" initially stacked *raw* `dim__`
values per target, not the *weighted contribution* (`weight × dim`) that
actually sums to the score — visually overstating a high-value/low-weight
dimension's real influence (e.g. literature at 0.98 with weight 0.10 would
render nearly as wide as genetics at 0.85 with weight 0.40). Caught during
the Phase 4 Playwright pass, not by static review — the component's own
docstring already promised "contributions that sum exactly to the score,"
which the raw-value version silently didn't deliver. Fixed by passing
`weights_used` from the ranking response into the table and computing
`contrib = weight × (dim ?? 0)` per segment, matching
`models/baseline.py`'s own formula. Confirmed visually afterward: Genetics
renders as the clearly dominant segment under the default scenario, as its
0.40–0.455 weight implies.

A related question resolved along the way: is `(dim ?? 0)` in a
contribution calculation a violation of "null is not zero" (invariant 1)?
No — `contrib__dim = dim.fill_null(0) * weight` is the actual, documented
scoring formula (`models/baseline.py`: "Nulls become zero only here").
Invariant 1 protects *displaying* a raw evidence value as if null meant
"measured zero"; a contribution is a different quantity, and null
genuinely contributing 0 to it is correct, not a display trick. The
distinction is now spelled out in the component's inline comment so a
future reader doesn't re-flag it as a regression.

### 2.4 The dark-mode dimension palette needed independent validation

`viz.py`'s comment claims its five colors were validated (adjacent-pair
and normal-vision CVD ΔE), which is true for the light-mode values reused
directly. A naive lightened variant for dark mode (chosen by eye) failed
the `dataviz` skill's validator outright: the dark OKLCH lightness band
(0.48–0.67) is narrower than light's (0.43–0.77), and three of five colors
landed outside it. Re-picked and re-validated independently
(`#2a78d6,#d9601f,#1baf7a,#b8790a,#cc4f81` against surface `#0e0f11`) — all
five checks pass. Recorded directly in `globals.css` as the exact
validator invocation, so it doesn't need re-deriving if the surface color
ever changes.

### 2.5 A target's score disagreed between the ranking row and its own evidence page

Found in review, not by any of the checks in §3/§4 — none of them compare
the same target across two pages. The ranking page resolves weights from
the active scenario (§4.4's URL state); the evidence and compare pages
each independently defaulted to `meta.default_weights`. Under the
research-focused default scenario the two happen to coincide closely
enough not to look obviously wrong, but under any other scenario they
diverge outright: LRRK2 read 0.8550 on a clinical-focused ranking row and
0.844 on the "View evidence" page one click away — same target, same
underlying fetch, two different silently-applied weight sets. Streamlit's
version didn't have this bug by construction: all three pages read a
single `st.session_state["weights"]`, which a page-based frontend has no
equivalent of.

Fixed by threading the ranking response's server-normalized `weights_used`
through the link itself rather than re-deriving weights at the
destination: `src/hooks/use-linked-weights.ts` adds
`linkedWeightsQueryString()` (used by the ranking table's "View evidence"
link and the ranking page's "Compare N selected" button) and
`useLinkedWeights()` (read by the evidence and compare pages). A page
reached without them — a bookmark, a fresh load — still falls back to
`meta.default_weights`, but now says so in a caption next to the score
rather than presenting the number as unconditional. Recorded as invariant
10 in `milestone5_plan.md` §3, since it's exactly the kind of
cross-page-consistency requirement that section exists to name. Regression
test: `e2e/smoke.spec.ts`'s "score matches the ranking row under a
non-default scenario" loads the ranking page under `scenario=clinical`,
reads the displayed score, follows the link, and asserts the evidence
page shows the same number — it fails against the pre-fix code (0.771 vs.
a default-weights recompute) and passes after.

### 2.6 The evidence-endpoint memoization attempt, reverted

Measured against real Parkinson's data: `/api/evidence` averages ~120ms,
dominated by the full 8,690-row re-sort `rank_for_disease(top_n=None)`
needs for the rank-of-N figure. A `(disease_id, weights)`-keyed
`lru_cache` wrapper was written and then reverted: it read
`cached_features()`/`cached_app_data()` from its own module rather than
through the call site, which silently defeated `tests/test_api.py`'s
`monkeypatch.setattr(main, "cached_features", ...)` pattern — the classic
"patch where it's used, not where it's defined" trap. An explicit-argument
version would need synthetic-data test isolation that doesn't yet exist
(shared module-level cache state reused across test functions with
different synthetic frames for the same `disease_id` risks silent
cross-test pollution). ~120ms × up to 4 parallel requests (the comparison
view's ceiling, capped by `MAX_COMPARE`) is accepted without a fix for
now; §4 of the plan records the reasoning in full.

## 3. Verified, and one thing that could not be

Every page was driven in a real browser against the real backend
(Playwright, headless Chromium) with real Parkinson's disease data, not
just typechecked:

- **Overview** — disease detail, evidence-coverage table, readout strip.
- **Ranking** — all five established Parkinson's genes surface near the
  top (LRRK2 #1, GBA1 #3, PARK7 #5, SNCA #6, PRKN #21), matching the
  Milestone 1 headline result under the new frontend's default scenario.
  Scenario switching (preset → Custom, slider drag via keyboard),
  filters, row-selection with a 4-target cap, CSV export label matching
  "N of total," and null dimensions rendering as em-dashes (not `0`) all
  confirmed against live responses.
- **Evidence** — contribution bars, radar (including a hollow/dashed
  vertex for a missing dimension, confirmed live for GBA1/PARK7's missing
  `functional` score in the comparison view, not just in a synthetic
  test), supporting/contradicting lists, drug info, source links.
- **Compare** — 3-target comparison built via direct URL and via the real
  ranking-page selection flow; remove button re-renders the grid and
  updates the URL; per-target missing-dimension handling confirmed
  correct in a real multi-target scenario (LRRK2 complete, GBA1/PARK7
  both missing `functional`).
- **Static export** — `make frontend-build` (`BUILD_STATIC_EXPORT=1 next
  build`) succeeds; `out/` contains six prerendered HTML pages with no
  external-origin references (checked by `scripts/check_frontend.py` and
  by hand).

**Not verified: the Docker image.** The Docker daemon was not running in
the build environment, and starting Docker Desktop was outside what this
session did without being asked. The `Dockerfile` was written carefully
against the working `.venv` (`uv sync --frozen` reconstructing what
`uv.lock` already records — the earlier `uv run pytest` failure during
this same session was traced to a stray `VIRTUAL_ENV` pointing at a
*different* environment, not a lockfile problem) and the verified static
export, but `docker build` / `docker run` have not actually been run
end-to-end.

The `Dockerfile` also changed after this section was first written: a
review pass caught that `pyproject.toml` declares `readme = "README.md"`
and `license = { file = "LICENSE" }`, which setuptools reads as static
metadata during `uv sync --frozen --no-dev` (the second sync, the one
that installs the project itself) — neither file was copied into the
image, so that layer would have failed outright. `COPY README.md LICENSE
./` was added ahead of it, but that fix itself has not been run through a
real `docker build`. If the build clears that step and then dies on an
OpenMP symbol at container startup, `python:3.11-slim` is missing
`libgomp1` (a common gap for images that ship xgboost/lightgbm) — add
`apt-get install -y --no-install-recommends libgomp1` to the runtime
stage if that's what surfaces. Whoever picks this up next should run
`make docker-build && make docker-run` and fix whatever that surfaces
before treating the container path as done.
